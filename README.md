# Pattern

A native SwiftUI photo and video library. Open `patternlock.xcodeproj` in Xcode 26.2 or later, select the `patternlock` scheme, and run on an iPhone or iPad with iOS 26.2 or later. The app and tests use the selected Xcode's iOS SDK. Keep the shared project in its current compatible format (`objectVersion = 77`) when saving it from newer Xcode versions.

## Languages

Pattern supports English, Korean, Japanese, French, German, Italian, and Simplified Chinese. It follows the device’s preferred app language, including the per-app language selection in iOS Settings. English is the fallback. `patternlock/Localizable.xcstrings` contains app text, accessibility labels, errors, and plural variations; `patternlock/InfoPlist.xcstrings` contains system permission explanations. StoreKit supplies localized prices. Vault/folder names, filenames, existing stored preferences, and recovery-phrase words are never translated. Only the suggested name for a new vault is localized.

Use `String(localized:)` for user-facing strings built outside SwiftUI’s localized literal APIs, and translate whole interpolated messages rather than joining translated words. Keep persisted identifiers and enum raw values stable. Add translations for all six languages when adding a message, and use catalog plural variations for counts. In Xcode, update the catalogs from source before translating. Run `python3 scripts/check-localizations.py` to check coverage and format arguments, or add `--stringsdata /path/to/DerivedData` after building to check compiler-extracted keys too. `LocalizationTests` checks the compiled resources, plural rules, and reordered interpolation in all seven languages.

## Included

- Welcome screens followed by a choice of 3×3, 4×4, or 5×5 grid, first-vault pattern confirmation, and recovery-phrase setup.
- A pattern lock on cold launch and every return from the background, using the chosen grid size.
- First-time pattern registration with a matching second entry; at least four unique dots are required.
- A privacy window hides the library and presented media before app-switcher snapshots.
- Different patterns open separate vaults, each with its own media, folders, and exports.
- Optional Face ID after the pattern, with a chosen existing vault displayed if Face ID fails.
- New vault creation with a name, unique pattern, and matching confirmation.
- Free use includes 3 albums (pattern vaults), with 5 photos/videos total in each. A one-time purchase removes both limits.
- Import multiple photos and videos through the system Photos picker, with progress and partial-failure reporting.
- After importing, keep the originals or choose **Delete originals from Photos** for successfully saved items, with Photos permission and system confirmation.
- Browse all media, photos, or videos. Sort by import date or filename.
- Create, rename, color, and delete folders. Move selected media between folders.
- Multi-select, select all, and permanently delete app copies with confirmation. Deleting a folder keeps its media in the library.
- Full-screen paging, pinch/double-tap photo zoom, and native video playback.
- Export original files through the system share sheet, including Save to Files and iCloud Drive destinations when available. Duplicate filenames are preserved with numbered suffixes.
- Per-vault settings for name, file count, storage usage, pattern changes, encrypted backups, recovery phrases, duress behavior, and vault deletion.

## Storage and backup

Each vault has its own original media, thumbnails, and versioned JSON manifest under `Library/Application Support/Vaults/<vault-id>`. The original library keeps its existing `Vaults/Personal` directory; new vaults use UUID directories. Imports are independent copies. Originals stay in Photos unless you explicitly choose to delete them after importing and confirm with Photos. Only originals with successfully committed, still-present vault copies are eligible; failed imports and items without Photos identifiers are never included. File operations run through an actor, manifests are written atomically, and deletion staging is recovered after an interrupted operation. Media and metadata request iOS complete file protection.

Deleting originals also affects iCloud Photos and synced devices. Deleted items may remain in Photos’ Recently Deleted collection for up to 30 days; Pattern does not empty it. Live Photo deletion is declined because the current importer saves only the still image, not the motion resource. If permission is denied, limited access excludes an original, or an asset cannot be deleted, the vault copies remain available. You can manage those originals directly in Photos. Locking, switching vaults, or backgrounding cancels a deletion request that is still waiting for permission.

**Local vaults are excluded from device backups.** Use **Back up to iCloud Drive** to save an encrypted `.patternbackup` archive through Files, then wait for its iCloud upload to finish. After deleting and reinstalling Pattern, onboarding starts again. Choose **Restore from iCloud**, select the saved archive in Browse → iCloud Drive, enter its original recovery phrase, and choose a new pattern. A recovery phrase alone cannot restore deleted media. This is a manual backup, not automatic backup or live iCloud sync. Pattern-derived encryption of the local media and additional app-wide settings remain future work.

Deleting the app removes its local vaults and installation key. iOS provides no uninstall callback and Keychain entries may outlive deletion, so the surviving credential ciphertext cannot be opened without the deleted installation key. On first credential access after reinstall, Pattern removes only its own old Keychain entry and starts onboarding with default settings. Saved iCloud backups, Photos originals, and StoreKit purchase ownership are unaffected. **Offload App** deliberately keeps the data container and is not deletion.

An in-place update keeps the installation key and vaults. The first upgrade from the previous unencrypted Keychain format migrates only when a local vault directory is present; an orphaned Keychain entry without local libraries is treated as a fresh install. Missing installation keys for the new encrypted format trigger a reset even if old local files were restored by the OS, ensuring restoration is explicit. Unreadable Keychain/files, malformed keys, and authentication failures lock the app instead of silently replacing data. Interrupted migrations can retry with the already-written installation key. Older device backups already outside the app are not retroactively erased.

No custom server or third-party dependency is required. StoreKit communicates with Apple for product prices, purchases, and explicit purchase restoration. Importing uses the system picker without requesting general Photos access. Read/write Photos permission is requested only when you choose to delete originals. Temporary export copies are removed when the share sheet closes.

## Pattern lock

Startup shows a neutral background while registration is checked. The returning-user pattern screen is never mounted during loading or onboarding. The onboarding save callback is explicitly main-actor isolated, and its store has an explicit deinitializer for the Swift 6.2/iOS 26.2 runtime compatibility issue.

On a fresh installation, three welcome pages introduce local storage, separate pattern-selected vaults, and manual encrypted backups. Users can skip the introduction or choose **Restore from iCloud**. Setup then asks for a grid size, a name for the first vault (Personal by default), a pattern drawn twice, and a recovery phrase. The generated phrase has 20 words; a custom phrase uses the existing minimum of 8 words and 40 characters. Users must repeat the whole phrase and confirm that they saved it outside the app before opening their vault. Copying a generated phrase uses a local-only clipboard item that expires after one minute. The grid, pattern verifier, and recovery verifier are saved in one Keychain write only at the end. No raw pattern or recovery phrase is persisted by onboarding. Backgrounding discards unfinished setup; if its final write already completed, returning requires the saved pattern.

Existing installations skip onboarding and retain their 5×5 grid, patterns, and media. The chosen grid applies to unlocking, creating/changing patterns, recovery, restoring backups, and pattern confirmations in settings. Inside a library, tap the vault name at the top and choose **New vault**. Enter a name, draw a new pattern, and repeat it to confirm. A pattern already assigned to a vault cannot be reused. Choose **Switch vault** or **Lock vault** from the same menu to return to the neutral lock screen; the next valid pattern opens its corresponding vault. An unknown pattern never creates a vault automatically.

Existing single-pattern installations are migrated atomically without moving or modifying their photos and folders. Cancelling new-vault setup returns to the previously unlocked vault. Backgrounding during setup discards the unconfirmed pattern and requires authentication again.

Draw a pattern, then draw it again to save it. Crossed dots are included automatically, and a dot cannot be reused in one gesture. VoiceOver users can select the dots individually and choose Use pattern.

Vault IDs, names, and a separately salted PBKDF2-HMAC-SHA256 verifier (600,000 iterations) for each pattern are stored in one atomic Keychain record with `kSecAttrAccessibleWhenUnlocked`; raw patterns are never persisted. The entire record is additionally encrypted with AES-256-GCM using a random installation key in `Library/Application Support/Installation/credential-key`, with complete file protection and exclusion from device backups. Vault names and contents are not listed on the lock screen. Five wrong attempts trigger a 30-second cooldown, with longer delays for further failures. Retry state survives app restarts. Keychain errors keep the library locked. **Recover vault** on the lock screen resets a pattern using the vault’s recovery phrase, when one has been configured. Recovery attempts share the persistent cooldown.

Backgrounding discards incomplete setup, requires a fresh unlock, dismisses library presentations, and invalidates outstanding export presentations. Brief interruptions such as a system permission prompt show the privacy cover without discarding an already unlocked session. A delayed authentication result cannot reopen the app after it has entered the background.

This is an application access lock. Existing media continues to use iOS file protection; it is not yet encrypted with a key derived from the pattern.

## Vault settings

Tap the gear in the library header, or choose **Vault settings** in the vault menu. Details show the current vault’s name, media count, and the total size of its local media, thumbnails, and manifest. Pattern changes require the current pattern, then the new pattern twice; a pattern already assigned to another vault is rejected. Changing or recovering a pattern, or deleting the vault, locks every open window using that vault. Windows share vault stores so imports, backups, and deletion cannot overlap on the same vault.

**Face ID & dummy vault** enables Face ID for the current vault. The flow is pattern → identify its vault → Face ID → library. Face ID is off by default. Choose another existing vault as the dummy before enabling it, confirm the current pattern, and confirm a newly selected dummy’s pattern. Enabling Face ID or changing settings while it is enabled requires successful Face ID. Selecting a protected vault as a new dummy also requires Face ID. Settings persist in the vault’s Keychain record. The app includes `NSFaceIDUsageDescription`; Face ID does not require an App ID capability.

A failed, cancelled, denied, or unavailable Face ID check displays the selected dummy directly, even if that dummy has its own Face ID or duress setting. **This never activates duress:** it does not revoke access, rotate recovery phrases, or change backups or sharing. Dummy sessions allow normal media operations, but hide vault settings and new-vault creation; use the dummy’s own pattern for full access. A system interruption or backgrounding leaves the app locked, and late biometric results are discarded. Device passcode and Touch ID cannot satisfy this Face ID check.

Deleting the selected dummy clears the selection but leaves Face ID enabled. A failed check then keeps the app locked; successful Face ID opens the protected vault so another dummy can be selected. If that pattern is also armed for duress and its dummy has been deleted, Face ID must succeed before opening the source vault or applying duress. Recovery resets the pattern without disabling Face ID.

**Pattern grid** in vault settings changes the grid for every vault. Select 3×3, 4×4, or 5×5; for each vault, confirm its current pattern on the old grid, then draw a unique new pattern twice on the new grid. Confirming current patterns does not activate duress. A successful Face ID check is also required if any vault has Face ID enabled. A final review saves every replacement and the grid in one Keychain update and locks every open window. Photos, folders, recovery phrases, Face ID, and duress settings stay intact. Cancelling, backgrounding, mismatched or missing patterns, a failed Face ID check, or a failed write leaves the grid and all old patterns unchanged. A concurrent vault/settings change requires restarting the wizard.

Recovery setup generates 20 random words (140 bits of randomness), or accepts a custom phrase of at least 8 words and 40 characters. The app requires the phrase to be repeated and the current pattern to be confirmed before saving. Ordinary recovery setup keeps only a salted PBKDF2 verifier in Keychain. A phrase generated automatically during a duress unlock is also retained in the protected Keychain record until the user confirms they saved it; it is never written to a file or included in a vault export. Custom phrases depend on the user choosing unpredictable words. Replacing a phrase invalidates the old phrase for local recovery; existing backups still require their original phrase.

**Back up to iCloud Drive** asks for the configured recovery phrase, encrypts the vault, and opens Files so the user can select iCloud Drive. Encryption is always enabled. The archive uses AES-256-GCM with a fresh 32-byte salt and a PBKDF2-HMAC-SHA256 key derived with 600,000 iterations. Media is processed in 1 MiB chunks; each encrypted record authenticates the header and its position, and a final authenticated marker detects truncation. Vault names, filenames, folders, and media are all encrypted. The format is versioned and restores reject altered data, missing files, invalid paths, and unsupported versions.

**Restore from iCloud**, available on onboarding, in settings, and on the lock screen, opens a user-selected encrypted archive from iCloud Drive through Files with the phrase used to create it. The system picker also supports locally downloaded copies and other providers; Pattern does not claim it can restrict that picker to iCloud. It creates a new vault with a unique name and newly confirmed pattern; existing vaults are never overwritten. Set up a new recovery phrase in the restored vault. Files handles cloud download/upload and provider errors; a successful export means Files accepted the save, not that iCloud has finished uploading it.

**Use a duress vault** marks the current vault and its existing pattern for duress. Setup explains the consequences and requires acknowledgment and the current pattern. It does not activate immediately. An unlock with that pattern displays the selected dummy, or the current vault if no dummy is selected. The displayed vault survives; every other vault’s local pattern and recovery credentials are atomically removed, including the trigger vault’s when a different dummy is selected. Duress generates a new recovery phrase for the surviving vault, disables new manual backups, and invalidates active export leases. With a selected dummy, duress does not wait for Face ID. All windows close existing presentations; revoked libraries also clear their cached state. In-flight exports and backup creation check revocation before exposing results. The local Vaults directory and existing child directories are excluded from future device backups, and this policy survives relaunch, disabling duress, or deleting/recreating the last vault.

Removed vault files are retained on disk, but their old patterns and phrases no longer recover them in Pattern. Restoring a separately saved encrypted backup is an explicit way to regain its contents in a new vault. This is local app access revocation, not cryptographic erasure of media or a concealment guarantee. **Save new recovery phrase** in settings requires the surviving vault’s pattern and confirmation that the phrase has been saved; the display copy is then removed from Keychain. Confirming patterns within settings does not trigger duress. Disabling duress only stops future activations; it does not undo prior revocations or re-enable backups. Earlier decoy configurations migrate to ordinary vaults so an upgrade cannot silently arm destructive behavior.

Sharing currently sends file copies through the system share sheet. Duress closes active sharing and removes temporary export files; it cannot revoke copies already delivered to recipients or Files providers, remove existing iCloud backups, or stop a provider upload already handed off. Automatic iCloud sync and access-controlled share links are not implemented. These limits are stated in duress setup and help.

**Delete this vault** requires typing the vault name and confirming its current pattern. It removes that vault’s local media and Keychain entry, leaving other vaults, Photos originals, and exported backups intact. Deletion stages the directory before committing the Keychain update; a failed update rolls back, and interrupted transactions are recovered or cleaned up on a later launch. Deleting the final vault returns to first-time setup.

## One-time purchase and free limits

Pattern is a free download with one **non-consumable** In-App Purchase: `jp.gm.patternlock.unlimited` (Pattern Unlimited). There are no subscriptions, recurring charges, or account servers. The free version allows three pattern-selected vaults, referred to as albums in purchase UI, and five combined photos/videos in each vault. Folders share their vault’s allowance; they do not create additional quotas. All existing privacy, recovery, and backup features remain available for free.

The upgrade and **Restore purchases** are available in vault settings. Reaching either limit also offers the upgrade. Batch imports save only the items that fit, report how many were skipped, and offer deletion from Photos only for successfully committed originals. Deleting app copies frees that album’s slots; deleting an album frees an album slot. Restoring a backup checks both the album count and the number of media items before installing anything. An oversized backup remains available for retry after purchasing; it is never silently truncated.

`StoreKitPurchaseClient` uses StoreKit 2’s on-device verification of Apple-signed transactions. Only `.verified` transactions with the expected product ID, app bundle ID, non-consumable type, and no revocation/expiration grant Unlimited. The app reads `Transaction.currentEntitlements(for:)` on launch and foregrounding, listens to `Transaction.updates`, and finishes verified transactions after delivering access. This follows [Apple’s StoreKit transaction verification model](https://developer.apple.com/documentation/storekit/transaction). There is no `verifyReceipt` endpoint, shared secret, custom validation server, or locally persisted “purchased” Boolean. Already verified purchases can be read from StoreKit’s local entitlement data without loading prices first. Buying and explicit restore still require Apple’s services; refunds become effective when StoreKit learns about them.

Pending approval, cancelled payment, unavailable products, and unverified transactions do not grant Unlimited. **Restore purchases** explicitly calls `AppStore.sync()` and re-reads verified entitlements; launch never triggers a sign-in prompt through `sync()`. Purchase restoration restores the license, not local photos. Restoring media remains the separate encrypted-backup flow. If Unlimited is lost, existing albums and media remain viewable, exportable, and deletable, even above the free limits; only new additions are limited.

Before shipping, create **Pattern Unlimited** in App Store Connect as a **Non-Consumable** with the exact ID `jp.gm.patternlock.unlimited`, choose its real price and availability, and complete Apple’s required product metadata/review. The app displays the localized price returned by StoreKit; no production price is embedded in the UI. The project marks the In-App Purchase capability as enabled. The bundled app does not contain a test entitlement or a paid-access bypass.

`StoreKit/Pattern.storekit` is a local development catalog containing just this one non-consumable. Its **$9.99 is a test-only placeholder**, not a selected release price. The Debug Run scheme uses it for local testing; local transactions never charge an Apple Account. Select **None** under Edit Scheme → Run → Options → StoreKit Configuration to test your App Store Connect product in Apple’s sandbox. StoreKit configuration files are ignored for App Store distribution. See [Apple’s setup guide](https://developer.apple.com/documentation/xcode/setting-up-storekit-testing-in-xcode).

Backup tests cover encrypted round trips over multiple chunks, wrong phrases, tampering, truncation, trailing data, missing media, unsafe paths, and restoring without replacing existing vaults. Verify iCloud Drive upload/download on a device signed into iCloud; the simulator checks do not exercise an iCloud account.
