# Pattern

A native SwiftUI vault for photos, videos, memos, and documents. Open `patternlock.xcodeproj` in Xcode 26.2 or later, select the `patternlock` scheme, and run on an iPhone or iPad with iOS 26.2 or later. The app and tests use the selected Xcode's iOS SDK. Keep the shared project in its current compatible format (`objectVersion = 77`) when saving it from newer Xcode versions.

## Languages

Pattern supports English, Korean, Japanese, French, German, Italian, and Simplified Chinese. It follows the device’s preferred app language, including the per-app language selection in iOS Settings. English is the fallback. `patternlock/Localizable.xcstrings` contains app text, accessibility labels, errors, and plural variations; `patternlock/InfoPlist.xcstrings` contains system permission explanations. StoreKit supplies localized prices. Vault/folder names, filenames, existing stored preferences, and recovery-phrase words are never translated. Only the suggested name for a new vault is localized.

Use `String(localized:)` for user-facing strings built outside SwiftUI’s localized literal APIs, and translate whole interpolated messages rather than joining translated words. Keep persisted identifiers and enum raw values stable. Add translations for all six languages when adding a message, and use catalog plural variations for counts. In Xcode, update the catalogs from source before translating. Run `python3 scripts/check-localizations.py` to check coverage and format arguments, or add `--stringsdata /path/to/DerivedData` after building to check compiler-extracted keys too. `LocalizationTests` checks the compiled resources, plural rules, and reordered interpolation in all seven languages.

## Included

- Welcome screens followed by a choice of 3×3, 4×4, or 5×5 grid, first-vault pattern confirmation, and recovery-phrase setup. Unfinished setup stays in memory while switching apps to save the phrase, preserving the current step and phrase until setup finishes or the app process ends.
- After setup, a pattern lock on cold launch and every return from the background, using the chosen grid size.
- First-time pattern registration with a matching second entry; at least four unique dots are required.
- A privacy window hides the library and presented media before app-switcher snapshots.
- Different patterns open separate vaults, each with its own media, folders, and exports.
- Optional Face ID after the pattern, with a chosen existing vault displayed if Face ID fails.
- New vault creation with a name, unique pattern, and matching confirmation.
- Free use includes 3 albums (pattern vaults), with 5 items total in each across all item types and folders. A one-time purchase removes both limits.
- **Add** opens a menu with **Media**, **Camera**, **Memo**, and **Document**. Each action saves into the current folder. New content appears under All, with separate Photos, Videos, Memos, and Documents filters.
- Camera offers Photo and Video modes directly into the vault without writing to Photos. In Photo mode, a small speaker button immediately left of the front/rear camera switch toggles shutter sound; the crossed-out icon selects silent capture. Toggling sound or switching cameras stops and reloads the camera scene. Silent capture uses an ARKit video frame on supported rear/front cameras, with lower detail than a full-resolution photo. Camera permission is requested on opening; microphone permission is requested for video. The sound toggle controls photos, not video audio. Captures stop when dismissed or backgrounded, and a failed vault save retains a temporary draft for retry or discard.
- Write a titled memo, saved as UTF-8 text, or copy multiple documents from Files, including on-device storage and available file providers. Original documents remain untouched. Memos open as text; documents use an embedded Quick Look preview with export controlled by the vault. Unsupported preview formats can still be stored and exported.
- Import multiple photos and videos through the system Photos picker, with progress and partial-failure reporting.
- After importing, keep the originals or choose **Delete originals from Photos** for successfully saved items, with Photos permission and system confirmation.
- Browse all media, photos, or videos. Sort by import date, filename, file date (newest first), largest first, or smallest first. File date uses photo EXIF or video creation metadata, then the original file’s modification/creation timestamp, then its import date if none is available. Size sorting uses original-file bytes; missing sizes go last. Older libraries are enriched on opening, and backups preserve these optional fields.
- Create, rename, color, and delete folders. Move selected media between folders.
- Multi-select, select all, and permanently delete app copies with confirmation. Deleting a folder keeps its media in the library.
- Full-screen paging, pinch/double-tap photo zoom, and native video playback with an expand control for full-screen portrait or landscape viewing. Playback pauses when leaving the page or backgrounding the app; Picture in Picture is disabled for vault media.
- Export original files through the system share sheet, including Save to Files and iCloud Drive destinations when available. Duplicate filenames are preserved with numbered suffixes.
- Per-vault settings for name, file count, storage usage, pattern changes, encrypted backups, recovery phrases, duress behavior, and vault deletion.

## Storage and backup

Each vault has its own original media, thumbnails, and versioned JSON manifest under `Library/Application Support/Vaults/<vault-id>`. The original library keeps its existing `Vaults/Personal` directory; new vaults use UUID directories. Imports are independent copies. Originals stay in Photos unless you explicitly choose to delete them after importing and confirm with Photos. Only originals with successfully committed, still-present vault copies are eligible; failed imports and items without Photos identifiers are never included. File operations run through an actor, manifests are written atomically, and deletion staging is recovered after an interrupted operation. Media and metadata request iOS complete file protection.

Deleting originals also affects iCloud Photos and synced devices. Deleted items may remain in Photos’ Recently Deleted collection for up to 30 days; Pattern does not empty it. Live Photo deletion is declined because the current importer saves only the still image, not the motion resource. If permission is denied, limited access excludes an original, or an asset cannot be deleted, the vault copies remain available. You can manage those originals directly in Photos. Locking, switching vaults, or backgrounding cancels a deletion request that is still waiting for permission.

**Local vaults are excluded from device backups.** In **Encrypted iCloud backup**, opt in separately for each owned vault and confirm its recovery phrase. CloudKit stores an encrypted backup in the user’s private database in `iCloud.jp.gm.patternlock`. Changes upload while that vault is open; reopening retries interrupted work. Reinstalling starts onboarding, where **Restore from iCloud** lists completed backups without a file picker. Select a backup, enter its recovery phrase, and choose a unique local name and pattern. Local originals remain available offline. This is automatic foreground backup and one-way sharing, not bidirectional personal-device synchronization. Pattern-derived encryption of local media remains future work.

Deleting the app removes its local vaults and installation key. iOS provides no uninstall callback and Keychain entries may outlive deletion, so the surviving credential ciphertext cannot be opened without the deleted installation key. On first credential access after reinstall, Pattern removes only its own old Keychain entry and starts onboarding with default settings. Saved iCloud backups, Photos originals, and StoreKit purchase ownership are unaffected. **Offload App** deliberately keeps the data container and is not deletion.

An in-place update keeps the installation key and vaults. The first upgrade from the previous unencrypted Keychain format migrates only when a local vault directory is present; an orphaned Keychain entry without local libraries is treated as a fresh install. Missing installation keys for the new encrypted format trigger a reset even if old local files were restored by the OS, ensuring restoration is explicit. Unreadable Keychain/files, malformed keys, and authentication failures lock the app instead of silently replacing data. Interrupted migrations can retry with the already-written installation key. Older device backups already outside the app are not retroactively erased.

No custom server or third-party dependency is required. StoreKit communicates with Apple for product prices, purchases, and explicit purchase restoration. Importing uses the system picker without requesting general Photos access. Read/write Photos permission is requested only when you choose to delete originals. Temporary export copies are removed when the share sheet closes.

## Pattern lock

Startup shows a neutral background while registration is checked. The returning-user pattern screen is never mounted during loading or onboarding. The onboarding save callback is explicitly main-actor isolated, and its store has an explicit deinitializer for the Swift 6.2/iOS 26.2 runtime compatibility issue.

On a fresh installation, three welcome pages introduce local storage, separate pattern-selected vaults, and optional encrypted iCloud backups. Finishing or skipping the introduction opens a **Create or restore** screen with **Create a new vault**, **Restore an existing vault**, and **Join shared vault** choices. Restore opens the encrypted-backup flow directly, using a saved iCloud backup and its original recovery phrase; it does not require creating an empty vault first. A **Restore from iCloud** shortcut is also available throughout the introduction. Creating a new vault then asks for a grid size, a name for the first vault (Personal by default), a pattern drawn twice, and a recovery phrase. The generated phrase has 20 words; a custom phrase uses the existing minimum of 8 words and 40 characters. Users must repeat the whole phrase and confirm that they saved it outside the app before opening their vault. Copying a generated phrase uses a local-only clipboard item that expires after one minute. The grid, pattern verifier, and recovery verifier are saved in one Keychain write only at the end. No raw pattern or recovery phrase is persisted by onboarding. Switching apps preserves the unfinished setup step and phrase in memory behind the privacy cover. Ending the app process discards unfinished setup; if its final write already completed, returning requires the saved pattern.

Existing installations skip onboarding and retain their 5×5 grid, patterns, and media. The chosen grid applies to unlocking, creating/changing patterns, recovery, restoring backups, and pattern confirmations in settings. The vault name sits beside the Pattern mark on the left of the library header, with action icons on the right in the same row. Tap the **New vault** icon to create another vault. Enter a name, draw a new pattern, and repeat it to confirm. A pattern already assigned to a vault cannot be reused. Tap the **Lock vault** icon to return to the neutral lock screen; the next valid pattern opens its corresponding vault. An unknown pattern never creates a vault automatically.

Existing single-pattern installations are migrated atomically without moving or modifying their photos and folders. Cancelling new-vault setup returns to the previously unlocked vault. Backgrounding during setup discards the unconfirmed pattern and requires authentication again.

Draw a pattern, then draw it again to save it. Crossed dots are included automatically, and a dot cannot be reused in one gesture. VoiceOver users can select the dots individually and choose Use pattern.

Vault IDs, names, and a separately salted PBKDF2-HMAC-SHA256 verifier (600,000 iterations) for each pattern are stored in one atomic Keychain record with `kSecAttrAccessibleWhenUnlocked`; raw patterns are never persisted. The entire record is additionally encrypted with AES-256-GCM using a random installation key in `Library/Application Support/Installation/credential-key`, with complete file protection and exclusion from device backups. Vault names and contents are not listed on the lock screen. Five wrong attempts trigger a 30-second cooldown, with longer delays for further failures. Retry state survives app restarts. Keychain errors keep the library locked. **Recover vault** on the lock screen resets a pattern using the vault’s recovery phrase, when one has been configured. Recovery attempts share the persistent cooldown.

Backgrounding preserves unfinished onboarding in memory, requires a fresh unlock, dismisses library presentations, and invalidates outstanding export presentations. Brief interruptions such as a system permission prompt show the privacy cover without discarding an already unlocked session. A delayed authentication result cannot reopen the app after it has entered the background.

This is an application access lock. Existing media continues to use iOS file protection; it is not yet encrypted with a key derived from the pattern.

## Vault settings

Tap the gear in the library header to open vault settings. The header contains New vault, Lock vault, and Settings. Above the media grid, the sort menu sits on the left and **Select** on the right; Select changes to **Done** while selection is active. Details show the current vault’s name, media count, and the total size of its local media, thumbnails, and manifest. Pattern changes require the current pattern, then the new pattern twice; a pattern already assigned to another vault is rejected. Changing or recovering a pattern, or deleting the vault, locks every open window using that vault. Windows share vault stores so imports, backups, and deletion cannot overlap on the same vault.

**App settings → App icon** offers nine abstract designs: Square, Triangles, Checker, Stripes, Rings, Diamonds, Waves, Hexagons, and Mosaic. Choose **Classic** to restore the original Pattern icon. This preference applies to the app on this device, across all vaults, and iOS persists it across launches. It changes the icon artwork; the app name remains Pattern. The picker reads the current icon from iOS and reports failed changes without marking them selected. Regenerate alternate artwork and previews with `swift scripts/generate-alternate-app-icons.swift`; Debug and Release both register the same alternate icon sets for iPhone and iPad.

**Face ID & dummy vault** enables Face ID for the current vault. The flow is pattern → identify its vault → Face ID → library. Face ID is off by default. Choose another existing vault as the dummy before enabling it, confirm the current pattern, and confirm a newly selected dummy’s pattern. Enabling Face ID or changing settings while it is enabled requires successful Face ID. Selecting a protected vault as a new dummy also requires Face ID. Settings persist in the vault’s Keychain record. The app includes `NSFaceIDUsageDescription`; Face ID does not require an App ID capability.

A failed, cancelled, denied, or unavailable Face ID check displays the selected dummy directly, even if that dummy has its own Face ID or duress setting. **This never activates duress:** it does not revoke access, rotate recovery phrases, or change backups or sharing. Dummy sessions allow normal media operations, but hide vault settings and new-vault creation; use the dummy’s own pattern for full access. A system interruption or backgrounding leaves the app locked, and late biometric results are discarded. Device passcode and Touch ID cannot satisfy this Face ID check.

Deleting the selected dummy clears the selection but leaves Face ID enabled. A failed check then keeps the app locked; successful Face ID opens the protected vault so another dummy can be selected. If that pattern is also armed for duress and its dummy has been deleted, Face ID must succeed before opening the source vault or applying duress. Recovery resets the pattern without disabling Face ID.

**Pattern grid** in vault settings changes the grid for every vault. Select 3×3, 4×4, or 5×5; for each vault, confirm its current pattern on the old grid, then draw a unique new pattern twice on the new grid. Confirming current patterns does not activate duress. A successful Face ID check is also required if any vault has Face ID enabled. A final review saves every replacement and the grid in one Keychain update and locks every open window. Photos, folders, recovery phrases, Face ID, and duress settings stay intact. Cancelling, backgrounding, mismatched or missing patterns, a failed Face ID check, or a failed write leaves the grid and all old patterns unchanged. A concurrent vault/settings change requires restarting the wizard.

Recovery setup generates 20 random words (140 bits of randomness), or accepts a custom phrase of at least 8 words and 40 characters. The app requires the phrase to be repeated and the current pattern to be confirmed before saving. Ordinary recovery setup keeps only a salted PBKDF2 verifier in Keychain. A phrase generated automatically during a duress unlock is also retained in the protected Keychain record until the user confirms they saved it; it is never written to a file or included in a vault export. Custom phrases depend on the user choosing unpredictable words. Replacing a phrase invalidates the old phrase for local recovery and prepares a new recovery envelope for the cloud backup. The new envelope is published on the next completed backup; until then, the old cloud copy still needs its old phrase. Exported backup files always retain their original phrase.

Cloud backup generates an independent random 20-word archive secret, stored only in the installation-bound Keychain registry. The user’s recovery phrase wraps that secret with AES-256-GCM and PBKDF2-HMAC-SHA256 (600,000 rounds, fresh 32-byte salt). Domain-separated authenticated metadata binds each archive to its cloud record. The archive encrypts names, folders, filenames, and original media in authenticated 1 MiB records with a final truncation marker. CloudKit receives a ciphertext CKAsset and encrypted metadata, never the raw recovery phrase or archive secret. A successful record save publishes both asset and metadata; a failed upload retains the previous completed backup. The current implementation uploads a full archive when the snapshot changes; incremental deduplication and historical versions are not implemented. **Export backup file** remains an optional portable alternative using the existing versioned `.patternbackup` format.

**Restore from iCloud** queries the signed-in Apple Account’s private CloudKit backups. Names remain encrypted; the chooser shows backup dates. Decryption verifies the recovery envelope, metadata, archive, and snapshot digest before installing anything. Restore creates a new vault; it never overwrites another local vault. Set up a new recovery phrase in the restored vault and opt in again if desired. **Import a backup file** continues to accept old `.patternbackup` files through Files and their original phrases. A phrase without a completed cloud backup or saved archive cannot recover deleted media.

**Use a duress vault** marks the current vault and its existing pattern for duress. Setup explains the consequences and requires acknowledgment and the current pattern. It does not activate immediately. An unlock with that pattern displays the selected dummy, or the current vault if no dummy is selected. The displayed vault survives; every other vault’s local pattern and recovery credentials are atomically removed, including the trigger vault’s when a different dummy is selected. Duress generates a new recovery phrase for the surviving vault, disables cloud backup/sharing and manual backups, queues all owned CloudKit shares for revocation in the same Keychain commit, and invalidates active export leases. With a selected dummy, duress does not wait for Face ID. All windows close existing presentations; revoked libraries also clear their cached state. In-flight exports and backup creation check revocation before exposing results. The local Vaults directory and existing child directories are excluded from future device backups, and this policy survives relaunch, disabling duress, or deleting/recreating the last vault.

Removed vault files are retained on disk, but their old patterns and phrases no longer recover them in Pattern. Restoring a separately saved encrypted backup is an explicit way to regain its contents in a new vault. This is local app access revocation, not cryptographic erasure of media or a concealment guarantee. **Save new recovery phrase** in settings requires the surviving vault’s pattern and confirmation that the phrase has been saved; the display copy is then removed from Keychain. Confirming patterns within settings does not trigger duress. Disabling duress only stops future activations; it does not undo prior revocations or re-enable backups. Earlier decoy configurations migrate to ordinary vaults so an upgrade cannot silently arm destructive behavior.

**Sharing** creates a separate encrypted copy per recipient, using a private CloudKit zone and a read-only `CKShare.Participant.oneTimeURLParticipant()`. An independent generated sharing phrase encrypts the one-time invitation URL and a random archive secret; a phrase-addressed public lookup record contains only this encrypted envelope. Apple enforces the one-recipient claim and read-only permissions. The owner can publish updates while the vault is open. **Join shared vault** is available in onboarding, on the lock screen, and in settings. Recipients set a local pattern and check CloudKit access before every open; there is no offline opening of received vaults. Access is rechecked every 30 seconds while open. The same Apple Account can import again with the original sharing phrase. Open limits are per local installation and survive normal relaunches; removal/reinstallation can reset that counter. Expiry/export/capture restrictions are client policies, not DRM. Capture detection can lock after a screenshot, but cannot prevent the first screenshot or an external camera. AirPlay playback is disabled. Revocation deletes the shared zone and invitation, with durable retries after network failures and duress. It cannot erase previously exported copies. Existing personal backups survive duress so they can be explicitly restored. See [CloudKit setup and device verification](docs/CLOUDKIT.md).

**Delete this vault** requires typing the vault name and confirming its current pattern. It removes that vault’s local media and Keychain entry, queues deletion of its configured cloud backup and owned shares, and leaves other vaults, Photos originals, and exported backup files intact. Removing a received vault only removes that local copy. Deletion stages the directory before committing the Keychain update; a failed update rolls back, and interrupted transactions are recovered or cleaned up on a later launch. Deleting the final vault returns to first-time setup.

## One-time purchase and free limits

Pattern is a free download with one **non-consumable** In-App Purchase: `jp.gm.patternlock.pro` (Pattern Unlimited). There are no subscriptions, recurring charges, or account servers. The free version allows three pattern-selected vaults, referred to as albums in purchase UI, and five combined photos/videos in each vault. Folders share their vault’s allowance; they do not create additional quotas. All existing privacy, recovery, and backup features remain available for free. Creating a share requires Unlimited; receiving a shared vault is free and does not consume owned-album/media quotas.

The upgrade and **Restore purchases** are available in vault settings. Reaching either limit also offers the upgrade. Batch imports save only the items that fit, report how many were skipped, and offer deletion from Photos only for successfully committed originals. Deleting app copies frees that album’s slots; deleting an album frees an album slot. Restoring a backup checks both the album count and the number of media items before installing anything. An oversized backup remains available for retry after purchasing; it is never silently truncated.

`StoreKitPurchaseClient` uses StoreKit 2’s on-device verification of Apple-signed transactions. Only `.verified` transactions with the expected product ID, app bundle ID, non-consumable type, and no revocation/expiration grant Unlimited. The app reads `Transaction.currentEntitlements(for:)` on launch and foregrounding, listens to `Transaction.updates`, and finishes verified transactions after delivering access. This follows [Apple’s StoreKit transaction verification model](https://developer.apple.com/documentation/storekit/transaction). There is no `verifyReceipt` endpoint, shared secret, custom validation server, or locally persisted “purchased” Boolean. Already verified purchases can be read from StoreKit’s local entitlement data without loading prices first. Buying and explicit restore still require Apple’s services; refunds become effective when StoreKit learns about them.

Pending approval, cancelled payment, unavailable products, and unverified transactions do not grant Unlimited. **Restore purchases** explicitly calls `AppStore.sync()` and re-reads verified entitlements; launch never triggers a sign-in prompt through `sync()`. Purchase restoration restores the license, not local photos. Restoring media remains the separate encrypted-backup flow. If Unlimited is lost, existing albums and media remain viewable, exportable, and deletable, even above the free limits; only new additions are limited.

The App Store Connect product is `jp.gm.patternlock.pro`, used as a **Non-Consumable** one-time unlock. Price and availability are managed in App Store Connect. The app requests this product with `Product.products(for:)` and displays Apple's `Product.displayPrice`, including the storefront's currency and formatting; no production price is embedded in the UI. Product loading, purchases, entitlement checks, transaction updates, and restoration all use the same ID. The project marks the In-App Purchase capability as enabled. The bundled app does not contain a test entitlement or a paid-access bypass.

The shared Run scheme has **StoreKit Configuration: None**, so normal development runs request the App Store Connect product through Apple's sandbox. `StoreKit/Pattern.storekit` remains a local development catalog for automated StoreKit tests, which activate it explicitly with `SKTestSession`. Its **$9.99 is a test-only placeholder**, not a selected release price. To test manually offline, select this file under Edit Scheme → Run → Options → StoreKit Configuration; switch back to **None** to fetch Apple's configured product and price. Local test transactions never charge an Apple Account. StoreKit configuration files are ignored for App Store distribution. See [Apple’s setup guide](https://developer.apple.com/documentation/xcode/setting-up-storekit-testing-in-xcode).

When diagnosing pricing in a Debug build, filter Xcode's console for `StoreKit`. Product requests log the returned product ID, display price, currency, storefront country, and type, or a missing-product/error result. These describe StoreKit's response and do not prove a fresh network request; StoreKit may cache product information. The UI clears the previous price during refresh and leaves purchasing unavailable if the refresh fails. If Xcode was open while the scheme changed on disk, verify **StoreKit Configuration: None** in its scheme editor before starting a new run.

## Verification

Run Product → Test in Xcode. Purchase tests cover verification, cancellation, pending approval, restore, refunds, stale results, quotas, partial imports, downgrade access, and restore limits. A StoreKitTest integration test exercises the local non-consumable catalog, signed entitlement verification, relaunch, and refund. Onboarding/grid tests cover all three sizes, swept dot detection, confirmation, recovery setup, atomic initial registration, legacy defaults, replacement of every vault pattern, duplicate/missing patterns, failed writes, Face ID, cancellation, concurrent changes, and preservation of media and access settings. Simulator builds must remain ad-hoc signed so Keychain entitlements are available. The XCTest target covers photo/video imports, original-byte preservation, persistence, folder operations, deletion, duplicate export filenames, rejected imports, unreadable manifests, interrupted-delete recovery, and exclusion from device backups. Pattern tests cover confirmation, gesture geometry, Keychain round trips, cooldown persistence, background/cold-launch locking, stale authentication results, and the privacy window lifecycle. Vault tests cover distinct-pattern routing, rejected duplicate patterns/names, confirmation and cancellation, legacy migration, and isolation of media, folders, deletion, and exports. File-protection attributes are checked on physical devices; the simulator does not emulate them.

Import-store tests use a fake Photos deletion service to verify explicit consent, partial imports, duplicate/missing identifiers, failed manifest writes, denied permission, cancellation, missing vault copies, and stale confirmations. On a device, also verify the Photos permission and deletion prompts with disposable photos/videos, including limited access and a Live Photo.

Settings tests cover renaming, current-pattern checks, recovery rotation and throttling, last-vault deletion, and Keychain failure recovery. Backup tests cover encrypted round trips over multiple chunks, wrong phrases, tampering, truncation, trailing data, missing media, unsafe paths, and restoring without replacing existing vaults. Cloud tests additionally cover opt-in behavior, secret separation, recovery-wrapper rotation, failure/retry, account changes, read-only enforcement, updates, offline access denial, persistent open counts, duress revocation, and interrupted invitations. These use an injected in-memory transport; real CloudKit claims and ACLs require the two-account device checks in docs/CLOUDKIT.md.

Face ID tests use an injected authenticator to cover delayed success, failure without duress side effects, restricted dummy sessions, protected/duress-marked dummies, settings authorization and persistence, single-use challenges, dummy deletion, interruptions, backgrounding, and stale results. Verify the actual Face ID permission and camera prompts on a Face ID-capable device, including a mismatch, Cancel, denied permission, and returning from the background.

Installation tests cover onboarding after deletion, real Keychain cleanup, encrypted credential storage, in-place upgrades, relaunches, interrupted migration/reset, corrupt keys, local backup exclusion, and explicit encrypted-archive restoration after reinstall.

Addition tests cover mixed memo/document persistence and encrypted-backup round trips, original-byte preservation, mixed-item quotas, partial document imports, failed-commit cleanup, extensionless exports, and capture draft disposal. On a physical device, verify photo/video capture, microphone permission, front/rear cameras, AR silent-photo orientation and shutter behavior, interruption/background cleanup, and that no capture appears in Photos. The simulator cannot exercise camera capture or ARKit. Also check Files imports from an iCloud provider and Quick Look previews for PDF and Office files.

Build and test with Xcode 26.2 (17C52) / iOS 26.2 or later. CloudKit development and production have separate schemas and data. A successful local build or fake-transport test is not evidence of a completed Apple upload or a cross-account claim; see the device verification checklist.
